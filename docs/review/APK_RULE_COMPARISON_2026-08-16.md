# APK 反编译资产与现有规则对照报告

状态：`review only / not production authorization`

日期：2026-08-16

适用 APK：SHA-256 `E4FB340EF0DAD857A018E2F06982D32623BDD683B22BD44230A2257C35DAA11C`

反编译报告：`apk-analysis/E4FB340E/APK_RULES_REPORT_ZH.md`

## 一、结论

APK 最有价值的部分不是 Android 外壳或界面资产，而是已经结构化抽出的加权池、条件、效果、武魂、魂兽和剧情索引。它适合作为新的 `REFERENCE DATA ONLY` 证据源和内容候选库，但不适合整包替换现有架构，也不能把 APK 当前控制流中的缺陷当作项目规则。

本次对照后的总分类如下：

| 分类 | 可以包含的内容 | 是否可直接进入 production |
| --- | --- | --- |
| 可直接化用 | 证据清单、稳定 ID/来源追踪方法、候选池先过滤后抽取、原子提交、防循环、已确认规则的交叉证据 | 只允许化用方法或证明现有规则；不自动新增内容和数值 |
| 需要审阅 | APK 独有武魂、魂兽、特殊天赋、身份数值、剧情、权重、requirements、effects、路线和终局 | 否；负责人确认后才能进入正式目录 |
| 明确不同 | 与现有已确认规则冲突，或数据模型/运行语义不同 | 否；默认维持现有规则，除非负责人另行变更决策 |
| 不纳入 | APK 外壳、加固/Hook 组件、二维码和转售警示图、已知不可达接线、未获授权的整段代码或文案 | 否 |

“可直接化用”是项目规则层面的判断，不等于已经确认第三方代码、文案或图片的复制授权。若 APK 不是项目自有资产，production 应优先采用独立实现和重写文案，只保存必要的来源证据。

## 二、真相源优先级

发生冲突时按以下顺序处理：

1. 用户提供并已确认的工作簿、文档和增量决定；
2. `docs/DECISION_RECORD_V2.md`、正式规则目录、production 配置和验收测试；
3. 当前可执行的 Player v2、年度事务、生产觉醒、独立战力和独立天赋运行时；
4. 本 APK 静态抽取结果，状态固定为 `reference_candidate`；
5. `data/reference/legacy-wheel/` 中的旧表、推断路由和推断流程。

APK 与第 1～3 层冲突时，不能用“APK 已经实现”作为覆盖现有决定的理由。

## 三、对照基线

### 3.1 现有项目

- Player v2 从 0 岁开始，`Player.age` 与世界时期分离；
- 6 岁使用 production 觉醒链，读取 271 项已审定武魂目录；
- 武魂形态固定为 `tool / beast / plant / food / body`，品质为 `low / ordinary / top / extreme`；
- 一次觉醒只抽一次共享品质，1～4 个武魂槽位分别抽形态和唯一目录实体；
- 战力是派生值，不写回 Player；0 级是永久不参战的 `civilian_observer`；
- 天赋系统与战力、Player v2、年度流程相互独立，特殊天赋、机会、遭遇和 91 级后魂核成长池仍为 `unresolved`；
- Event Schema v2 已有 wheel/flow/route 协议，运行时已支持 `roll / gate / dispatchWheel / repeatWheel / end`；
- route state 模块已存在，但通用 flow 运行时尚未执行 `setRoute / yieldYear / terminal`；
- authoritative v2 effects 当前只允许 3 个数值路径、5 个 set 路径和 8 个实体集合 add 路径。

### 3.2 APK

- 61 个唯一静态数据根；
- 4,781 条池记录、41,637 条选项记录；这些包含版本副本，不能相加为唯一可玩内容；
- 584 条武魂 option 记录；
- 243 条魂兽原始记录，其中当前基础入口 215 条、辅助熊类 12 条、休眠蹄类 16 条；
- 107 条魂兽结构化语义；
- 107 个剧情节点，共 490 个剧情选项；
- 44 种已抽取 effect type；
- 正式引擎采用 seed + cursor 的 `pcg32-counter-v1`。

## 四、可直接化用

### 4.1 可直接作为 reference 证据层

以下文件可以继续直接用于检索、交叉核验和生成审阅材料：

- `derived/catalogs/martial-souls.csv`；
- `derived/catalogs/soul-beast-species-raw.csv`；
- `derived/catalogs/soul-beast-species.csv`；
- `derived/catalogs/story-timeline.csv`；
- `derived/catalogs/pools.csv`、`options.csv`、`effects.csv`、`requirements.csv`；
- `derived/pretty/*.js` 及关键源码行号索引；
- APK 哈希、ZIP 条目清单和静态提取报告。

这些文件应保持只读来源状态，不应直接改造成 `data/v2/` production 配置。后续若迁入 `data/reference/apk/E4FB340E/`，必须保留哈希、原路径、抽取时间、来源层和 `productionEligible: false`。

### 4.2 可直接沿用的工程原则

下列原则与现有架构一致，可以直接用来补强实现和测试，不涉及新的平衡决定：

1. 建池时先过滤 `enabled`、内容等级、时代/内容包和 trigger，再进行加权抽取；
2. 使用稳定 ID，而不是显示名称或相邻编号建立跳转；
3. 整组 effects 在克隆状态上执行，全部成功后再提交；
4. 抽取和自动流程必须有明确的次数上限、池耗尽结果和稳定错误码；
5. 保存 seed、抽取序号、实际候选和实际权重，确保问题可复现；
6. 源码存在、正式导入、入口可达和运行成功必须分开记录；
7. 休眠、门控、staging 和旧源副本不能计入当前 production 内容量。

### 4.3 可直接作为现有规则交叉证据

- APK 与现有项目的先天魂力到天赋等级映射一致：`0→F，1→E，2–3→D，4–5→C，6–7→B，8–9→A，10→S，20→神级`。这只能证明映射一致，不能证明概率一致。
- 将 APK 武魂显示文本去除品质前缀和括号规则后，得到 564 个基础名称；其中 109 个与现有 271 项 production 目录同名。
- 109 个同名项中，58 个的基础形态和品质也与现有 production 定义一致。它们可以作为现有定义的交叉证据，不需要再次导入，也不能借此自动覆盖属性、族谱、canonLevel 或负责人审定记录。
- 候选池过滤、加权抽取、注入 RNG、克隆后应用和年度原子提交等总体方向与现有实现一致。

## 五、需要审阅

### 5.1 武魂内容

归一化对照结果：

| 项目 | 数量 | 处理 |
| --- | ---: | --- |
| APK 基础名称 | 564 | 仅作为候选总池 |
| 与 production 同名 | 109 | 逐项比对，不重复建定义 |
| 同名且形态、品质一致 | 58 | 作为交叉证据；现有定义保持真源 |
| 同名但形态或品质冲突 | 44 | 必须负责人审阅；默认维持现有定义 |
| 同名但 APK 分类无法完整映射 | 7 | 必须审阅特殊池、变异、概念或血脉语义 |
| APK 独有基础名称 | 455 | 必须做去重、形态、品质、属性、canonLevel 和来源权利审阅 |

冲突不是少量例外。例如昊天锤、七杀剑、蓝银皇、九宝琉璃塔等在 APK 中常被标为“顶级”，现有 production 则已确认成 `extreme`；“死灵圣法神”还存在 `beast` 与 `body` 的形态冲突。不能用 APK 分类批量改写现有 271 项目录。

APK 独有项中混有明显跨作品、概念型和恶搞项。主模式仍只允许 `canon + expanded`；`crossover + parody` 即使保留，也只能进入未来独立娱乐模式。

### 5.2 出生身份

APK 与 `talent.docx`/当前天赋配置明显具有共同来源，但不是同一版本：

- 平民、自由魂师、骑士、贵族、皇室、宗门子弟、神之子、神明转世、穿越者、气运之子的核心概念大体对应；
- APK 增加开局货币，当前配置多未采用；
- APK 的“一无所有之人”固定先天魂力 1 且禁特殊天赋，当前已确认规则为固定 5；
- APK 的“重生者”是额外元素/领域抽取，当前规则是第二人生继承并重新生成同名实体；
- 当前“乡下平民”“魂师的孩子”“皇家骑士团团长的孩子”“贵族子女”的命名和部分效果口径与 APK 不同。

因此身份名称可用于建立来源对应表，但权重、货币、固定值和 effects 均需审阅。

### 5.3 特殊天赋

当前项目的 `specialTalents` 为空并明确标记 `unresolved`。APK 当前正式池有 9 条候选，其中双生武魂停用，实际有效 8 条：三生武魂、道心通明、先天领域雏形、人兽混血、神明转世、真龙血脉、亚龙血脉、地龙血脉。

这些条目可以直接进入审阅清单，但不能直接填入空池，原因包括：

- 双生/三生武魂会与现有“按先天魂力抽取 1～4 个武魂”的 production 规则重叠；
- 身份固定天赋、特殊天赋数量和武魂数量之间尚无统一优先级；
- 领域、神考、血脉武魂和人兽混血都需要新的实体及 Player 写入协议；
- APK 旧源与当前正式池本身也存在 9 项/11 项、启用/停用差异。

### 5.4 魂兽

现有魂兽工作簿有 210 个不重复候选，210 个全部仍为 `待审定`，确认字段为空，不能视为 production 目录。

将 APK 原始物种文本去除括号说明后得到 240 个不重复名称：

- 其中 212 个属于当前基础入口；
- 107 个有结构化血脉/属性/融合语义；
- 与现有 210 项审阅表只重合 18 个名称；
- 与当前基础入口重合 17 个；
- 与 APK 结构化语义表重合 11 个。

这说明 APK 魂兽数据不是对旧工作簿的小修补，而是一套高度互补的新候选源。所有物种、类别、权重、血脉、属性和融合语义都应进入合并审阅，而不是直接导入。

### 5.5 剧情和路线

APK 的 107 个剧情节点共 490 个选项：

| 路线 | 池 | 选项 | 年龄范围 |
| --- | ---: | ---: | --- |
| 斗一史莱克 | 43 | 224 | 6～25 |
| 斗一武魂殿 | 32 | 153 | 14～25 |
| 斗二小霍娘 | 27 | 96 | 11～25 |
| 斗二魂兽 | 5 | 17 | 文本/状态条件 |

这些数据适合快速搭建剧情审阅包，但每个节点都必须审阅：

- 选项文案需要内容、语气和复制权检查；
- 原有战力阈值、死亡、自动胜利和跳过主线语义需要改写为现有战斗结果轮盘协议；
- `timelineAge` 必须映射到 `worldEra + Player.age`，不能覆盖 Player 年龄；
- 主线、势力、NPC、神位和个人路线应落入现有 route lane，而不是压成单个分支数字；
- 史莱克正常入口在 APK 中缺失映射，不能照抄当前接线；
- 斗二其他主线受发布旗标门控，不能计为当前可玩路线。

### 5.6 requirements、effects 和状态模型

APK 的条件和 effects 覆盖等级、魂兽年限、属性阶段、血脉、地区、武魂、领域、神位、神考、魂骨、货币、库存、NPC 好感、战力、死亡和结局。当前 authoritative Event Schema v2 的通用 effect 写入面远小于 APK。

应按下一阶段实际内容逐类扩展 typed effect 和 trigger，不应一次性复制 44 种 effect type。优先级建议为：

1. `flags / counters / inventory / currency / NPC relation`；
2. `soulRings / soulBones / bloodlines / attribute progression`；
3. `route transition / death / ending`；
4. 神考、神位、神器和复杂条件效果。

每一类都要先定义 Player 真源、校验器、原子提交、回滚和测试，再允许内容使用。

## 七、不应化用的 APK 当前缺陷和非目标资产

以下项目应保留为证据或缺陷案例，不进入实施清单：

1. 斗一史莱克 option 未映射为分支 1；
2. 斗一时期选择没有写入剧情时间轴；
3. 魂兽入口绕过共享时期处理器；
4. 极致武魂门槛被最终构建器清除；
5. 双生、武魂变异、先天道体在不同版本池之间不一致；
6. 蹄类只有休眠路由，熊类只是辅助池；
7. 未发布的斗二主线和未出现的斗三入口；
8. Android 加固、Hook、Xposed、原生库和二次封装组件；
9. 二维码、转售警示图和与核心玩法无关的壳资源。

## 八、推荐决策

1. 把 APK 固定为第三套只读证据源：`current confirmed > APK reference > legacy inferred`；
2. 先完成武魂差异表、魂兽合并审阅、特殊天赋审阅和一条主线剧情审阅，不先重写通用引擎；
3. 第一条剧情建议选择斗一史莱克作为 6～25 岁内容脊柱，因为年龄覆盖最完整；不沿用 APK 的缺失入口，而使用现有 route state 显式接线；
4. 第一版只实现被这条路线直接证明需要的 trigger/effect/route 能力；
5. 人类 0 岁到神界的主模式闭环优先于斗二、魂兽、多主线和娱乐模式扩容；
6. 每批内容必须携带 `sourceRefs`、`reviewStatus`、`canonLevel`、审定人和版本号；
7. 所有 APK 文案默认重写，数值默认重新审定，代码默认独立实现。

本报告只完成对照与工作目标输入，不授权修改 production 数据、实现功能、暂存、提交或推送。
